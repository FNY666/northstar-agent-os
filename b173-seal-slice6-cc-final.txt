How the seal was produced (not hand-written)
scripts/seal-delivery.py drives the repository's own CodePhaseMachine:
  - materialises commit a49d073f as an actual patch on its start commit 38d175e9
    (git worktree at the start commit + git apply of the real diff);
  - replays the host-declared checks against that patched tree, recording each
    check through the phase machine's begin_check/complete_execution protocol;
  - lets the phase machine write delivery-seal.json, patch-replay.json,
    patch-audit.json and phases.json.
Every field of the seal (start commit, start tree hash, check-input pins, patch
digests) is produced by the same code that produces a live run's seal.
The tool refuses a delivery whose patch does not apply to the start commit and
refuses to emit a seal when a host check fails; it never falls back to writing a
plausible-looking receipt.

One finding worth flagging
The committed evidence is deliberately NOT under the protocol's reserved
delivery-evidence/ directory name. build_blind_bundle refuses a start commit
that tracks any path under that directory, and the rule is blanket over the
whole tree -- so committing the seal there would have made EVERY future blind
bundle fail, including the one for this very delivery. The committed files
carry prefixed names (slice6-seal.json and friends) instead, and
CommittedEvidenceDoesNotBreakFutureBundlesTests pins that invariant.

Open items and limits

  host checks passed against the patched tree, and that the pinned check inputs
  were unchanged. It does not prove the Slice 6 implementation is correct.

  defect. Pinning a functional test-command manifest remains open.
